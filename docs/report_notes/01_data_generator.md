# โมดูล 1: สร้างข้อมูลสมมุติ (บันทึกสำหรับเล่มรายงาน)

> ใช้เขียน **บทที่ 2 หัวข้อ "ลักษณะข้อมูล"** เป็นหลัก ไม่ใช่เทคนิค DE ในบทที่ 3
> เกณฑ์อนุญาตให้ "สร้างข้อมูลสมมุติที่สมเหตุสมผลเพื่อใช้ทดสอบงานของโปรแกรม"
> ตัวเลขทั้งหมดดูได้จาก `docs/data_issues.md` (สร้างอัตโนมัติ)

## 1. ทำไมต้องสร้างข้อมูลเอง

- ข้อมูลร้านค้าจริงหาได้ยากและมีข้อมูลส่วนบุคคล (ชื่อสมาชิกในข้อมูลนี้สุ่มขึ้นเองและไม่ซ้ำกัน)
- ข้อมูลจาก Kaggle ส่วนใหญ่ถูกทำความสะอาดมาแล้ว **จึงแทบไม่มีปัญหาให้ใช้เทคนิค DE**
- การสร้างเองทำให้**รู้คำตอบที่ถูกต้อง** (มีไฟล์เฉลย) จึงวัดได้ว่า pipeline จับปัญหาได้กี่ % ซึ่งตรงกับการวัดคุณภาพแบบ Simple ratio ใน Ch3

## 2. เรื่องสมมุติ (ใช้เล่าในบทนำหรือบทที่ 2)

ร้านกาแฟ "Doi Brew" มี 3 สาขาในเชียงใหม่ **แต่ละสาขาซื้อระบบ POS คนละยี่ห้อ** ข้อมูลจึงออกมาคนละรูปแบบ เจ้าของร้านอยากรู้ภาพรวมทั้ง 3 สาขา (เมนูไหนขายดี, สาขาไหนยอดตก, ลูกค้ากลุ่มไหนซื้อบ่อย) แต่รวมข้อมูลเองไม่ได้ ซึ่งตรงกับตัวอย่างร้านขาย widget หลายสาขาในสไลด์ Ch1

## 3. ลักษณะข้อมูล (Input ของ pipeline)

| ไฟล์ | รูปแบบ | 1 แถวคือ | จำนวน | จุดเด่น |
|---|---|---|---|---|

**ชนิดข้อมูลตาม Ch2** (ใส่ในเล่มเพื่อแสดง Data discovery)
- Nominal: สาขา, เมนู, หมวด, ช่องทางชำระ, เพศ
- Ordinal: ขนาดแก้ว (S < M < L)
- Ratio: จำนวน, ราคา, อายุ
- Interval: วันเวลา

## 5. ปัญหาที่ใส่ไว้ (สรุป)

รวม **25 ประเภท** แบ่งเป็น 3 กลุ่ม (ตารางเต็มพร้อมจำนวนอยู่ใน `docs/data_issues.md`)
- **กลุ่ม A (7 ข้อ):** เกิดจากรูปแบบไฟล์ต่างกัน → แก้ทั้งหมดในโมดูล 2 (Extract + Integration)
- **กลุ่ม B (15 ข้อ):** ข้อมูลซ้ำ ค่าว่าง ค่าผิดกฎ ข้อมูลไม่สอดคล้อง → ตรวจในโมดูล 3 (Quality) แก้ในโมดูล 4 (Clean)
- **กลุ่ม C (3 ข้อ):** outlier ที่เป็นข้อผิดพลาด 2 แบบ + **outlier ที่เป็นของจริง 1 แบบ (ห้ามลบ)** → โมดูล 4

## 6. Input → Process → Output

- **Input:** ค่าตั้งต้นด้านบนของ `generate.py` (ช่วงวันที่, จำนวนสมาชิก, สัดส่วนปัญหา, seed = 42)
- **Process:** 5 ขั้น
  1. สร้าง Master data (สินค้า วันหยุด)
  2. สร้างสมาชิกแบบสะอาด (อายุขึ้นกับสาขาประจำ)
  3. จำลองการขายรายวัน (จำนวนบิลใช้การแจกแจงแบบ Poisson ปรับตามสาขา วันในสัปดาห์ วันหยุด ปิดเทอม)
  4. ใส่ปัญหาแล้วจดลงไฟล์เฉลย
  5. เขียนออกเป็นรูปแบบของแต่ละสาขา
- **Output:** ไฟล์ 6 ไฟล์ใน `data/raw/` + ไฟล์เฉลยใน `data/generator_log/` (`injected_issues.json`, `sales_truth.csv`, `members_truth.csv`) + `docs/data_issues.md`

## 7. ภาพหน้าจอที่ควรเก็บ

1. ตัวอย่าง 5 แถวแรกของ `nimman_sales.csv` (เปิดใน Excel หรือ VS Code)
2. `cmu_sales.xlsx` ที่เห็นหัวคอลัมน์ภาษาไทยและชื่อเมนูสะกดต่างกัน
3. `thaphae_sales.json` 1 บิลที่เห็นโครงสร้างซ้อนชั้น
4. เทียบ 3 ไฟล์ข้างกันเพื่อแสดงปัญหากลุ่ม A (**ภาพสำคัญที่สุด** ใช้ในสไลด์ได้ด้วย)
5. `members.csv` ที่เห็นเบอร์โทรหลายรูปแบบ

## 8. คำถามที่อาจารย์อาจถาม

**ถาม: ข้อมูลสมมุติน่าเชื่อถือแค่ไหน**
ตอบ: ปัญหาทุกข้อมีสาเหตุที่เกิดได้จริง (เช่น POS ส่งซ้ำตอนเน็ตหลุด, พนักงานพิมพ์เอง, กรอก พ.ศ. ในช่อง ค.ศ.) และสัดส่วนปัญหาตั้งไว้ต่ำ (0.2-10%) เหมือนข้อมูลจริง

**ถาม: รู้ได้อย่างไรว่า pipeline ทำงานถูก**
ตอบ: เก็บข้อมูลสะอาดและรายการปัญหาทุกแถวไว้เป็นเฉลย จึงวัดได้ว่าจับปัญหาได้กี่ % และเติมค่าว่างได้ใกล้ค่าจริงแค่ไหน

**ถาม: ทำไมใส่ออเดอร์ใหญ่ที่ไม่ใช่ข้อผิดพลาด (C3)**
ตอบ: สไลด์ Ch4 บอกว่า outlier บางตัวเป็นของจริง (Natural) ถ้าลบทิ้งหมดจะเสียข้อมูลจริง เราจึงใส่ไว้เพื่อทดสอบว่าวิธีตรวจ outlier แยกข้อผิดพลาดออกจากของจริงได้หรือไม่

**ถาม: ทำไมรันกี่ครั้งก็ได้ข้อมูลเหมือนเดิม**
ตอบ: ใช้ random seed คงที่ (42) ทุกคนในกลุ่มและอาจารย์จึงได้ข้อมูลชุดเดียวกัน
