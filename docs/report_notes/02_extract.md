# โมดูล 2: Extract + Integration (บันทึกสำหรับเล่มรายงาน)

> ใช้เขียน **บทที่ 3 (เครื่องมือและเทคนิค)** ส่วนแรกของ pipeline
> โค้ด: `pipeline/extract.py` / รัน: `py -3.13 -m pipeline.extract`
> ผลลัพธ์: `data/processed/sales_staging.csv` (ตาราง Staging 16,447 แถว)

## ภาพรวม

ขั้นตอน ETL ใน Ch1 คือ `Extract → Staging Area → Transform → Load` โมดูลนี้ทำช่วง **Extract → Staging Area** คือพาข้อมูลจาก 3 สาขาที่รูปแบบต่างกันมารวมเป็นตารางเดียวที่มีโครงสร้างเดียวกัน

**หลักการ:** โมดูลนี้แก้เฉพาะปัญหาที่เกิดขึ้น**ทั้งไฟล์อย่างเป็นระบบ** (กลุ่ม A) เพราะถ้าไม่แก้ก็รวมตารางไม่ได้ ส่วนความผิดพลาด**บางแถว** (ซ้ำ ว่าง ผิดกฎ) จะ**ไม่แตะเลย** เพื่อให้โมดูล 3 วัดคุณภาพได้ครบ ถ้าแปลงค่าไม่ได้จะปล่อยว่าง เก็บค่าดิบไว้ในคอลัมน์ `*_raw` และติดธงใน `extract_flags`

```
nimman_sales.csv   cmu_sales.xlsx   thaphae_sales.json
      │                  │                │ (แตก JSON)
      └── Schema mapping + แปลงวันเวลา / รหัสสินค้า / ขนาด / ชำระเงิน / ราคา ──┘
                              │
                     Integration (ต่อตาราง) + ตรวจยอด
                              │
                  sales_staging (16,447 แถว, 18 คอลัมน์)
```

|---|---|---|---|---|---|---|---|
| นิมมาน | CSV | 7,162 แถว | 7,162 | 7,162 | 0 | 0 | ✅ |
| มช. | Excel | 4,048 แถว | 4,048 | 4,048 | 0 | **121** | ✅ |
| ท่าแพ | JSON | 3,733 บิล | 5,237 | 5,237 | 0 | 0 | ✅ |

- **จับคู่สินค้าไม่ได้ 121 แถว = ชื่อเมนูสะกดผิด (B14) ครบทุกแถวพอดี** (ตรวจกับไฟล์เฉลยแล้ว) จะแก้ในโมดูล 4

## เทคนิคที่ 1: Schema mapping (แก้ A1)

**ปัญหา:** 3 สาขาตั้งชื่อคอลัมน์ต่างกันและต่างภาษา เช่น จำนวนสินค้าเป็น `qty` / `จำนวน` / `quantity` ถ้าต่อตารางตรง ๆ จะได้ 3 คอลัมน์แยกกันและข้อมูลว่างเต็มตาราง

**เทคนิค:** กำหนด **โครงสร้างกลาง (Global schema)** แล้วเขียนตารางจับคู่ชื่อคอลัมน์ของแต่ละสาขา (`SCHEMA_MAP` ใน `extract.py`)
- อ้างอิง: **Ch5 Data Integration** แนวคิด **Global-as-View (GAV)** คือนิยามแต่ละคอลัมน์ของโครงสร้างกลางจากคอลัมน์ของแหล่งข้อมูล / Lab 2 ข้อ 5 (เปลี่ยนชื่อคอลัมน์)

| โครงสร้างกลาง | นิมมาน | มช. | ท่าแพ |
|---|---|---|---|
| `receipt_id` | `receipt_no` | `เลขที่บิล` | `receipt_id` |
| `sale_datetime` | `sale_datetime` | `วันที่` + `เวลา` | `timestamp` |
| `product_raw` | `item_code` | `ชื่อเมนู` | `items[].sku` |
| `qty` | `qty` | `จำนวน` | `items[].quantity` |
| `unit_price` | `unit_price` | *(ไม่มี)* | `items[].price` |
| `line_total` | *(ไม่มี)* | `ราคารวม` | *(ไม่มี)* |
| `member_id` | `member_id` | `รหัสสมาชิก` | `customer.member_id` |
| `payment_raw` | `payment` | `ชำระโดย` | `payment.method` |

**วัตถุประสงค์:** ให้ทุกสาขาพูด "ภาษาเดียวกัน" ก่อนรวม และเก็บการจับคู่ไว้ในตารางเดียว ถ้าเพิ่มสาขาใหม่ก็แค่เพิ่มแถวในตาราง ไม่ต้องแก้โค้ดส่วนอื่น

## เทคนิคที่ 2: แตก JSON เป็นตาราง (แก้ A6)

**ปัญหา:** ไฟล์ท่าแพ 1 ก้อนคือ 1 บิล ข้างในมีรายการสินค้าซ้อนอยู่ (`items: [...]`) ซึ่งนำไปวิเคราะห์ด้วยตารางแถว-คอลัมน์ไม่ได้

**เทคนิค:** `pd.json_normalize(record_path="items", meta=[...])` แตกให้ 1 สินค้า = 1 แถว แล้วคัดลอกข้อมูลระดับบิล (เวลา สมาชิก ชำระเงิน) ไปทุกแถวของบิลนั้น
- อ้างอิง: **Ch2 Data mapping** "Web data might arrive in the form of hierarchical JSON ... need to be translated into row and column data"

**Input → Output:**
```
{"receipt_id": "TP-190E4A", "timestamp": "2026-01-01T00:12:00Z",
 "items": [{"sku": "DB-BAK-CHC", "quantity": 1, "price": 85}]}
                          ↓
receipt_id | datetime_raw         | product_raw | qty | unit_price | source_row
TP-190E4A  | 2026-01-01T00:12:00Z | DB-BAK-CHC  | 1   | 85         | receipts[0].items[0]
```
**ผล:** 3,733 บิล → 5,237 แถว

## เทคนิคที่ 3: แปลงวันเวลาเป็น ISO 8601 เวลาไทย (แก้ A2)

**ปัญหา:** วันเวลา 3 รูปแบบ ถ้าไม่แปลงจะเรียงลำดับหรือเปรียบเทียบข้ามสาขาไม่ได้ และเวลาท่าแพจะช้าไป 7 ชั่วโมง ทำให้กราฟยอดขายรายชั่วโมงผิด

| สาขา | ก่อน | วิธีแปลง | หลัง |
|---|---|---|---|
| นิมมาน | `01/01/2569 07:06` (วว/ดด/พ.ศ.) | แยกส่วนด้วย regex แล้ว**ลบ 543 ปี** | `2026-01-01 07:06:00+07:00` |
| มช. | `2026-01-01` + `07:14` (แยกคอลัมน์) | **รวม 2 คอลัมน์**เป็นค่าเดียว | `2026-01-01 07:14:00+07:00` |
| ท่าแพ | `2026-01-01T00:12:00Z` (UTC) | **แปลง timezone** UTC → Asia/Bangkok (+7 ชม.) | `2026-01-01 07:12:00+07:00` |

- อ้างอิง: **Ch1** ตัวอย่างร้าน widget "Transform the date from local time to ISO 8601" / **Ch2** Data mapping "Convert format of date-time data" / **Lab 5 ข้อ 8** (ทำรูปแบบวันที่ให้สอดคล้องกัน)
- **ตรวจความถูกต้อง:** เทียบเวลาทุกบิลกับไฟล์เฉลย ตรงทั้งหมด (ยกเว้น 15 บิลที่ตั้งใจใส่เวลาผิดไว้ B11)

## เทคนิคที่ 4: Translation mapping (แก้ A3, A4, A7)

**ปัญหา:** ค่าเดียวกันแต่ละสาขาเขียนต่างกัน ถ้าไม่แปลง `M`, `กลาง`, `Medium` จะถูกนับเป็น 3 ค่า และจะรวมยอดขายของ "ลาเต้" ข้ามสาขาไม่ได้

| เรื่อง | นิมมาน | มช. | ท่าแพ | ค่ามาตรฐาน | ตารางที่ใช้ |
|---|---|---|---|---|---|
| สินค้า (A3) | `C03` | `ลาเต้` | `DB-COF-LAT` | `P03` | `products.csv` (Master data) |
| ขนาด (A4) | `M` | `กลาง` | `Medium` | `M` | `SIZE_MAP` |
| ชำระเงิน (A7) | `QR` | `พร้อมเพย์` | `promptpay` | `qr` | `PAYMENT_MAP` |

- อ้างอิง: **Ch2 Translation and Mapping** "Representing codes can be mapped to the relevant values" (เหมือนตัวอย่างแปลงรหัสคณะ 05 เป็น "Science")
- **ออกแบบให้จับคู่แบบตรงตัวเท่านั้น** ถ้าไม่เจอในตารางจะปล่อยว่างและติดธง `product_unmatched` ไม่เดา
- **ผล:** จับคู่สินค้าไม่ได้ 121 แถว ทั้งหมดเป็นชื่อเมนูสะกดผิดของ มช. เช่น `BROWNIE`, `brownie`, `CHOCOLATE CAKE` หรือชื่อที่มีช่องว่างเกินหน้าหลัง (มองด้วยตาเหมือนถูก แต่คอมพิวเตอร์เห็นว่าไม่เท่ากัน)

**วัตถุประสงค์และเหตุผลที่ไม่แก้ชื่อสะกดผิดตอนนี้:** ชื่อสะกดผิดเป็นความผิดพลาด**บางแถว** (กลุ่ม B) ถ้าแก้ตอนนี้ ปัญหาจะหายไปก่อนถูกวัด ปล่อยไว้ให้โมดูล 3 วัดเป็นตัวเลข แล้วโมดูล 4 แก้ จึงเล่าในเล่มได้ครบ **"เจอปัญหา → วัด → แก้"**

## เทคนิคที่ 5: Attribute construction ด้านราคา (แก้ A5)

**ปัญหา:** นิมมานกับท่าแพเก็บ**ราคาต่อชิ้น** ส่วน มช. เก็บ**ราคารวม** ถ้ารวมตารางตรง ๆ คอลัมน์ราคาจะมีความหมายไม่เท่ากัน

**เทคนิค:** สร้างคอลัมน์ที่ขาดจากคอลัมน์ที่มี ให้ทุกแถวมีทั้ง `unit_price` และ `line_total`
- นิมมาน, ท่าแพ: `line_total = qty × unit_price`
- มช.: `unit_price = ราคารวม ÷ จำนวน`
- บันทึกที่มาใน `price_source` (`file` = มาจากไฟล์ / `derived_from_total` = คำนวณจากราคารวม)
- อ้างอิง: **Ch2 Attribute Construction** (เหมือนตัวอย่างสร้าง BMI จากส่วนสูงและน้ำหนัก)

**ผล:** มาจากไฟล์ 12,182 แถว / คำนวณได้ 4,002 แถว / **คำนวณไม่ได้ 263 แถว** ได้แก่
- นิมมาน 217 แถว: ราคาว่าง (B6 212 แถว + แถวซ้ำของแถวเหล่านั้น 5 แถว)
- มช. 46 แถว: จำนวนว่าง (B8 40 แถว) หรือจำนวนเป็น 0 ซึ่งหารไม่ได้ (6 แถวจาก B10)

ส่วนนี้โมดูล 4 จะเติมจากตารางราคาต่อ

**ข้อสังเกต (สำคัญสำหรับโมดูล 4):** สาขา มช. ถ้าพนักงานพิมพ์**จำนวน**ผิด (C1 เช่น 1 → 100) ราคารวมก็จะผิดตามไปด้วย (65 → 6,500) พอคำนวณกลับ ราคาต่อชิ้นจึง**ยังถูกต้อง** (6,500 ÷ 100 = 65) ตรวจแล้ว 12 แถวเป็นแบบนี้ทั้งหมด แปลว่า**ดูจากราคาต่อชิ้นอย่างเดียวจะไม่เห็นความผิดปกติ ต้องดูที่จำนวนหรือราคารวม** ในทางกลับกัน ถ้าพิมพ์**ราคา**ผิด (C2) ราคาต่อชิ้นที่คำนวณได้จะผิดชัดเจน (×100) โมดูล 4 จึงต้องตรวจ outlier หลายคอลัมน์ ไม่ใช่คอลัมน์เดียว

## เทคนิคที่ 6: Data Integration + ตรวจยอด

**เทคนิค:** ต่อ 3 ตารางที่โครงสร้างเหมือนกันแล้วเป็นตารางเดียว (`pd.concat` แบบ Lab 2 ข้อ 1) พร้อมติดป้ายที่มาทุกแถว (`branch`, `source_file`, `source_row`) และ**ตรวจยอด** ว่าแถวที่ออกเท่ากับแถวที่อ่านเข้า ถ้าไม่เท่าโปรแกรมจะหยุดและแจ้ง error
- อ้างอิง: **Ch5** Data integration "data from many sources goes to a single centralized location" / **Ch1** ตัวอย่าง widget "Add a field to tag the location" และ **Load verification** / **Ch3 Data Auditing** (ย้อนกลับไปหาแถวต้นฉบับได้)

**วัตถุประสงค์:** ได้ตารางเดียวที่ตอบคำถามภาพรวมทั้ง 3 สาขาได้ และมั่นใจว่าไม่มีข้อมูลหายระหว่างทาง

## เรื่องชนิดข้อมูลตอนอ่านไฟล์ (Data discovery, Ch2)

| ไฟล์ / คอลัมน์ | ถ้าอ่านแบบปกติจะเกิดอะไร | วิธีที่ใช้ |
|---|---|---|
| `members.csv` / `phone` | `0812345678` กลายเป็น `812345678` **เลข 0 หาย** | บังคับเป็นข้อความ |
| `members.csv` / `birth_year` | มีค่าว่าง จึงกลายเป็นทศนิยม `2004.0` | ใช้ `Int64` (จำนวนเต็มที่ว่างได้) |
| `cmu_sales.xlsx` / `เลขที่บิล` | เลข 13 หลักอาจถูกแปลงเป็นตัวเลข | บังคับเป็นข้อความ |

## โครงสร้างตาราง Staging (18 คอลัมน์)

- **ข้อมูลหลัก:** `branch`, `receipt_id`, `sale_datetime`, `product_id`, `size`, `qty`, `unit_price`, `line_total`, `member_id`, `payment`
- **ข้อมูลช่วยตรวจสอบ:** `price_source`, `extract_flags`, `datetime_raw`, `product_raw`, `size_raw`, `payment_raw`, `source_file`, `source_row`
- หมายเหตุ: **ไม่มีคอลัมน์ลำดับสินค้าในบิล** เพราะไฟล์นิมมานและ มช. ไม่มีข้อมูลนี้ จึงไม่สร้างขึ้นเอง

## ภาพหน้าจอที่ควรเก็บ

1. ผลรันคำสั่ง `py -3.13 -m pipeline.extract` (ตารางรายงานการ Extract)
2. ตาราง `SCHEMA_MAP` ในโค้ด (แสดง Schema mapping)
3. **Before / After ของวันเวลา 3 สาขา** (คอลัมน์ `datetime_raw` คู่กับ `sale_datetime`)
4. แถวที่ติดธง `product_unmatched` (แสดงว่าระบบไม่เดา)
5. บิลท่าแพ 1 บิลในไฟล์ JSON เทียบกับแถวที่แตกออกมาในตาราง staging

## คำถามที่อาจารย์อาจถาม

**ถาม: ทำไมไม่ลบข้อมูลซ้ำและแก้ชื่อสะกดผิดในขั้นนี้เลย**
ตอบ: ขั้นนี้คือ Staging area ต้องเก็บข้อมูลให้ครบก่อน ถ้าลบตอนนี้จะวัดไม่ได้ว่าข้อมูลเดิมมีปัญหากี่ % (Data Quality Assessment ใน Ch3) เราแยกให้ชัดว่ากลุ่ม A (ต่างทั้งไฟล์) แก้ที่นี่ ส่วนกลุ่ม B (ผิดบางแถว) วัดในโมดูล 3 และแก้ในโมดูล 4

**ถาม: รู้ได้อย่างไรว่าไม่มีข้อมูลหายระหว่างรวมตาราง**
ตอบ: ตรวจยอดทุกครั้ง แถวที่ออกต้องเท่ากับแถวที่อ่านเข้า (16,447 = 16,447) ถ้าไม่เท่าโปรแกรมจะหยุดทันที และทุกแถวมี `source_file` + `source_row` ย้อนกลับไปดูต้นฉบับได้

**ถาม: ทำไมต้องแปลงเวลาท่าแพ ถ้าไม่แปลงจะเป็นอย่างไร**
ตอบ: ไฟล์ท่าแพเก็บเวลา UTC ซึ่งช้ากว่าเวลาไทย 7 ชั่วโมง ถ้าไม่แปลง ลูกค้าตอน 8 โมงเช้าจะกลายเป็นตี 1 กราฟช่วงเวลาขายดีจะผิดทั้งหมด และโมดูล 4 จะเข้าใจผิดว่าเป็นการขายนอกเวลาเปิดร้าน

**ถาม: Global-as-View กับ Local-as-View ต่างกันอย่างไร และทำไมเลือก GAV**
ตอบ: GAV นิยามโครงสร้างกลางจากแหล่งข้อมูล ส่วน LAV นิยามแหล่งข้อมูลแต่ละแหล่งจากโครงสร้างกลาง เราเลือก GAV เพราะแหล่งข้อมูลมีจำนวนน้อยและคงที่ (3 สาขา) การเขียนว่าคอลัมน์กลางมาจากคอลัมน์ไหนของแต่ละสาขาจึงตรงไปตรงมาที่สุด

**ถาม: ทำไมเบอร์โทรต้องอ่านเป็นข้อความ**
ตอบ: เบอร์โทรไม่ใช่ตัวเลขที่นำไปคำนวณ (เป็น Nominal ตาม Ch2) ถ้าอ่านเป็นตัวเลข เลข 0 ข้างหน้าจะหาย ข้อมูลจะผิดตั้งแต่ขั้นแรก
