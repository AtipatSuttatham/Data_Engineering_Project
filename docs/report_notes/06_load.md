## ภาพรวม

ขั้น **L** ของ ETL ตาม Ch1: `Extract → Transform → **Load** → Data Repository → Analytics`
โมดูล 7, 8, 9 จะอ่านข้อมูลจากฐานข้อมูลนี้ ไม่เรียก pipeline ใหม่

**ทำไมใช้ SQLite:** เก็บทั้งฐานข้อมูลในไฟล์เดียว มากับ Python อยู่แล้ว ไม่ต้องติดตั้งเซิร์ฟเวอร์ ใช้คำสั่ง SQL ได้เหมือนฐานข้อมูลใหญ่ และอาจารย์เปิดตรวจได้ทันที

สไลด์ Ch1 แบ่งเรื่อง Load เป็น 2 ส่วน โมดูลนี้ทำครบทั้งสองส่วน
1. **วิธีโหลด 3 แบบ:** Initial loading / Incremental loading / Full refresh
2. **Load verification:** Missing or null values / Server performance / Load failures

## เทคนิคที่ 1: ออกแบบโครงสร้างฐานข้อมูล (Schema) ด้วยกุญแจและกฎ (Ch1)

เขียนคำสั่ง `CREATE TABLE` เองทุกตาราง **ไม่ปล่อยให้ pandas สร้างให้อัตโนมัติ** เพราะต้องกำหนดกุญแจและกฎได้เอง

**Primary key / Foreign key (Star schema จากโมดูล 5)**
```
                  dim_date (PK: date_key)
                        ▲ FK
 dim_product ◄── FK ── fact_sales ── FK ──► dim_member
 (PK: product_id)   (PK: sale_line_id)    (PK: member_id)
                        │ FK
                        ▼
                  dim_branch (PK: branch_id)
```
- **Primary key:** ห้ามซ้ำ ใช้ระบุแถว / **Foreign key:** ต้องมีค่าอยู่ในตารางที่อ้างถึง
- อ้างอิง: Ch1 "Establishing key relationships across tables"
- **SQLite ปิดการตรวจ Foreign key ไว้เป็นค่าเริ่มต้น** โค้ดจึงต้องเปิดเองทุกครั้งที่เชื่อมต่อ (`PRAGMA foreign_keys = ON`) ถ้าไม่เปิด กุญแจจะไม่มีผลเลย

**กฎตรวจข้อมูลในฐานข้อมูล (CHECK constraint)** เป็น**ด่านสุดท้าย**ที่นำกฎคุณภาพจากโมดูล 3 มาใส่ในฐานข้อมูล
| กฎในฐานข้อมูล | ตรงกับกฎคุณภาพ |
|---|---|
| `qty > 0`, `unit_price > 0`, `line_total > 0` | VL1 |
| `gender IN ('M','F','U')` | VL5 |
| `size IN ('S','M','L')` หรือว่าง | – |
| `age BETWEEN 10 AND 100` | VL4 |
| `UNIQUE (receipt_id, product_id)` | UQ1 |
| `NOT NULL` ในคอลัมน์สำคัญ | CP2, CP3 |

**ทดสอบแล้ว:** ใส่จำนวน 0 หรือติดลบ, ราคา 0, ขนาด "XL", รหัสสินค้าที่ไม่มีอยู่ หรือเมนูซ้ำในบิลเดียว → **ฐานข้อมูลปฏิเสธทุกกรณี**

**ชนิดข้อมูล:** SQLite ไม่มีชนิดวันที่และ boolean โดยตรง จึงเก็บ
- วันที่ / วันเวลาเป็น `TEXT` รูปแบบ ISO 8601 เช่น `2026-01-15T08:32:00+07:00` (**เก็บ timezone ไว้ด้วย**) รูปแบบนี้เรียงลำดับเป็นข้อความได้ถูกต้องตามเวลา
- จริง/เท็จเป็น `INTEGER` 0/1

**Index:** สร้างที่คอลัมน์ Foreign key ของ fact_sales (วันที่, สาขา, สินค้า, สมาชิก) ให้การค้นหาและ join เร็วขึ้น (Ch1 Server performance / Ch9 Poor performance)

**View `v_sales_enriched`:** join fact กับ dimension ทุกตารางไว้ล่วงหน้า ให้ Dashboard query ได้ง่าย

## เทคนิคที่ 2: วิธีโหลด 3 แบบ (Ch1)

| วิธี | ความหมาย (Ch1) | ใช้ที่ไหน | เหตุผล |
|---|---|---|---|
| **Initial loading** | โหลดข้อมูลทั้งหมดครั้งแรก | ทุกตาราง ตอนรัน `run_load()` | ฐานข้อมูลยังว่าง |
| **Full refresh** | ลบข้อมูลเดิมแล้วโหลดใหม่ทั้งตาราง | dimension และตารางสรุป | ตารางเล็ก และค่าเปลี่ยนได้ทั้งตาราง (เช่น ยอดสะสมของลูกค้าเปลี่ยนทุกวัน) ลบแล้วโหลดใหม่ง่ายกว่าไล่แก้ทีละแถว |
| **Incremental loading** | โหลด**เฉพาะข้อมูลใหม่**ต่อท้าย | fact_sales | ตารางใหญ่ที่สุดและโตขึ้นทุกวัน ถ้า Full refresh ทุกครั้งจะช้าลงเรื่อย ๆ |

**ลำดับการโหลด:** dimension ก่อน fact (เพราะ fact อ้างถึง dimension) ส่วนการลบกลับกัน คือลบ fact ก่อน

### สาธิต Incremental loading ⭐
สมมุติว่าร้านส่งข้อมูลเป็นรายเดือน

| รอบ | ส่งมา | เพิ่มจริง | ในฐานข้อมูล |
|---|---|---|---|
| 1 Initial (ม.ค.–พ.ค.) | 13,507 | 13,507 | 13,507 |
| 2 Incremental (มิ.ย.) | 2,746 | **2,651** | 16,158 |
| 3 รันซ้ำ (มิ.ย. อีกครั้ง) | 93 | **0** | 16,158 |
| ตรวจ: เทียบกับโหลดทั้งหมดทีเดียว | | | **เหมือนกันทุกแถว ✅** |

**อธิบายตัวเลข:**
- **Watermark:** ระบบจำวันที่ล่าสุดที่โหลดแล้ว (`date_key` สูงสุด) รอบถัดไปส่งเฉพาะข้อมูลตั้งแต่วันนั้น
- รอบ 2 ส่งมา 2,746 แถว แต่เพิ่มจริง 2,651 แถว เพราะส่ง**วันที่ 31 พ.ค. ซ้ำไปด้วย 95 แถว** (ใช้ ≥ วันล่าสุด เผื่อวันล่าสุดโหลดไม่ครบ) แถวซ้ำถูกข้ามอัตโนมัติ
- รอบ 3 ส่งมา 93 แถว (วันที่ 30 มิ.ย.) แต่**เพิ่ม 0 แถว** แปลว่ารันซ้ำกี่รอบก็ไม่เกิดข้อมูลซ้ำ เรียกว่า **Idempotent** ทำได้เพราะกฎ `UNIQUE(receipt_id, product_id)` คู่กับ `INSERT OR IGNORE`
- คุณสมบัตินี้ป้องกันปัญหาเดียวกับ**บิลซ้ำ (B2)** ที่เราเจอในข้อมูลท่าแพ ซึ่งเกิดจากระบบ sync ส่งข้อมูลซ้ำ

### Transaction: กันการโหลดสำเร็จครึ่งเดียว
การโหลดทั้งหมดอยู่ใน **Transaction** เดียว ถ้าเกิดข้อผิดพลาดกลางทาง ฐานข้อมูลจะ**ย้อนกลับเป็นสภาพเดิมทั้งหมด (Rollback)**
- **ทดสอบแล้ว:** ตั้งใจใส่จำนวนติดลบในแถวสุดท้ายของ fact_sales แล้วสั่งโหลด → ฐานข้อมูลปฏิเสธ → **ข้อมูลเดิมทุกตารางยังอยู่ครบ** ไม่มีตารางไหนถูกลบ หรือโหลดไปได้ครึ่งเดียว → ประวัติการโหลดบันทึกว่า "failed"
- อ้างอิง: Ch1 Load verification "Load failures"

**ทำไมตรวจค่าว่างด้วย "จำนวนเท่าก่อนโหลด" ไม่ใช่ "ต้องเป็น 0":** บางคอลัมน์ว่างได้โดยถูกต้อง เช่น member_id ว่าง = ลูกค้าทั่วไป หรือ revenue ว่าง 3 วัน = ข้อมูลหาย (โมดูล 5) สิ่งที่ต้องตรวจคือการโหลด**ไม่ทำให้ค่าว่างเพิ่มหรือหาย** เช่น ถ้า NULL กลายเป็น 0 ระหว่างโหลด วันที่ข้อมูลหายจะกลายเป็น "ขายได้ 0" ซึ่งผิด

**ตารางประวัติการโหลด `etl_load_log`:** บันทึกทุกครั้งที่โหลด (เวลา, ตาราง, วิธีโหลด, จำนวนแถวก่อน/หลัง, สำเร็จ/ล้มเหลว, ข้อความ error) ใช้ตรวจย้อนหลังได้ (Ch3 Data auditing)

## ภาพหน้าจอที่ควรเก็บ

1. โครงสร้างตารางใน **DB Browser for SQLite** (แท็บ Database Structure) ที่เห็น Primary key / Foreign key
2. ตารางผล **Load verification** (ผลรัน `py -3.13 -m pipeline.load`)
3. **ตารางสาธิต Incremental loading** (4 แถว)
4. ตาราง `etl_load_log`
5. ผลของ SQL ตัวอย่าง "วันหยุดขายดีกว่าวันธรรมดาเท่าไร" (มีประเด็นให้เล่า)
6. ข้อความ error ตอนฐานข้อมูลปฏิเสธข้อมูลผิด (แสดงว่า CHECK ทำงาน)

## คำถามที่อาจารย์อาจถาม

**ถาม: ทำไมต้องมี CHECK ในฐานข้อมูล ในเมื่อทำความสะอาดข้อมูลแล้ว**
ตอบ: เป็นด่านสุดท้าย ถ้าอนาคตโค้ดส่วน transform มี bug หรือมีคนใส่ข้อมูลเข้าฐานข้อมูลโดยตรง ข้อมูลผิดจะถูกปฏิเสธทันที ไม่เข้าไปปนเงียบ ๆ

**ถาม: Incremental loading ต่างจาก Full refresh อย่างไร และเลือกอย่างไร**
ตอบ: Full refresh ลบแล้วโหลดใหม่ทั้งหมด ง่ายและไม่มีข้อมูลค้าง แต่ช้าเมื่อข้อมูลใหญ่ Incremental โหลดเฉพาะส่วนใหม่ เร็วแต่ต้องจัดการเรื่องข้อมูลซ้ำ เราใช้ Full refresh กับตารางเล็กที่ค่าเปลี่ยนได้ทั้งตาราง และ Incremental กับตารางขายที่ใหญ่และโตทุกวัน

**ถาม: ถ้าโหลดซ้ำโดยไม่ตั้งใจ จะเกิดข้อมูลซ้ำไหม**
ตอบ: ไม่เกิด เพราะมีกฎ UNIQUE(เลขที่บิล, สินค้า) คู่กับ INSERT OR IGNORE ทดสอบแล้วว่ารันซ้ำได้ 0 แถวเพิ่ม (Idempotent)

**ถาม: ถ้าโหลดล้มเหลวกลางทางจะเกิดอะไร**
ตอบ: ทุกการโหลดอยู่ใน Transaction เดียว ฐานข้อมูลจะย้อนกลับเป็นสภาพเดิมทั้งหมด และบันทึกว่าล้มเหลวในตารางประวัติ ทดสอบแล้วด้วยการตั้งใจใส่ข้อมูลผิด

**ถาม: ทำไมเก็บวันเวลาเป็นข้อความ**
ตอบ: SQLite ไม่มีชนิดวันที่โดยตรง เอกสารของ SQLite แนะนำให้เก็บเป็นข้อความรูปแบบ ISO 8601 ซึ่งเรียงลำดับได้ถูกต้องและเก็บ timezone ได้ เราตรวจแล้วว่าอ่านกลับมาได้เวลาเดิมทุกแถว
